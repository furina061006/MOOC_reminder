# 教训：给"别人的扩展"排障的一次翻车记录（GinsMooc 案例）

> 入口索引与工作约定在仓库根目录 [`AGENTS.md`](../../AGENTS.md)；本文件是 `.dsh/agents/` 知识库的一部分。

**状态**：全是事后复盘。`【事实】` 都标了当时的取证方式；`【待验证】` 是没做完的部分。

**这份文档为什么存在**：2026-10-16 我花了十几轮去修 `reference_projects/GinsMooc/`（**别人写的、另一个扩展**）在平台换新前端后"按钮不出现"的问题，反复误判、改坏过、最后被原作者的新版本取代。技术结论对**任何扩展排障**都适用，所以留档；**但结论本身不要当成现行事实**——参考项目已由上游修好，本仓库不留它的任何代码或工具。

**先说边界**：GinsMooc 与本仓库（MOOC Reminder）是**两个不同的扩展**。它靠**页面 DOM 选择器**工作，本仓库靠**页面内同源 XHR**取 API。同一场平台改版，对两边的破坏面完全不同——**它坏了不代表本仓库要跟着改**。

## 一、被排障对象长什么样（原作者的实现，值得先读懂）

一个内容脚本包打天下，生命周期只有五步。**记住它的形状，才能判断"哪里断了"**：

| 步骤 | 做法 | 断了的症状 |
| --- | --- | --- |
| ① 注入 | `manifest.json` 的 `matches` 决定脚本是否进入页面 | 页面上**一点痕迹都没有**（连注入的 `<style>`、标记节点都没有） |
| ② 挂载 | 建 `#GinsMooc` 容器，插进页面某个内容容器 | 有痕迹、**没有容器** |
| ③ 感知 | 100 ms 轮询 + `hashchange`，从 URL 与 DOM 读状态 | 容器在、**按钮不显隐** |
| ④ 显隐 | 靠**加/删一个 CSS 类**来隐藏/显示按钮 | 按钮全露或不露，但 DOM 都在 |
| ⑤ 取答案 | 从 DOM 认出题目 → 把题目标识发给作者服务器 → 把答案写回 DOM | 按钮在、**点了没反应** |

原作者的实现有个很值钱的设计：③④ 之间用**一个布尔量**（"准备页壳是否还挂着隐藏类"）来推断"现在是不是答题页"，④ 只是它的函数。**所以那个布尔量的语义一旦被改，显隐就会跟着乱。** 这一点我付出了三轮回滚的代价才记住（见第四节）。

## 二、【事实】排障第一原则：先分层，别急着改代码

**同一个症状（"按钮没出现"）至少对应 5 类互不相干的断点**，而且每类都要用不同手段查：

| 层 | 判据（在目标页 Console 里直接测） | 修法 |
| --- | --- | --- |
| ① 注入 | 页面里有没有该扩展留下的**任何**痕迹（注入的 `<style>`、标记节点、自定义元素） | 改 `matches` / 查扩展是否真的加载了你想的那份 |
| ② 挂载 | 扩展的根节点在不在 DOM、父容器是谁 | 换容器选择器 |
| ③ 方法/API 存在性 | 调用的方法在这个页面环境里存在吗 | 换等效原生 API |
| ④ 路由/事件 | 状态变化靠的事件还会不会触发 | 补 `pushState`/`popstate` 等 |
| ⑤ CSS 类语义 | 用来隐藏/显示的那个类，**页面里还有定义吗** | 补自己的样式 |

**教训**：我当时一头扎进 ②，改挂载点、加兜底容器，而真正没通的是 ①（注入规则）。**改了三轮才回头查第一层。** 正确顺序是**从外往里**：先证明"脚本进没进来"，再谈它进来之后干了什么。

**一条特别省事的判据**：扩展在挂载前通常已经往页面里插过东西（样式、标记节点）。

- 连那些都没有 → **脚本一行没跑**，此时改选择器/CSS/逻辑全是白改；
- 有痕迹、没有按钮 → 才轮到挂载及其后。

## 三、【事实】"没注入"最容易被误判，且最常见的真因是匹配规则

**误判一**：用开发者工具 Elements 面板的 `Ctrl+F` 搜插件名，搜到了就以为"注入了"。

**它会把样式表里的文本一起搜出来**（比如 `#GinsMooc { … }` 这段 CSS 里就含那个名字）。必须用 `document.querySelector('#根节点id')` 才算数。

**误判二**：拿文档语义推断匹配规则。

当时的规则是 `…/*learn/*?tid=*`。权威文档说路径部分是对"**路径 + 查询串**整体做 glob、`*` 可跨任意字符"，按这个读法它应该能匹配 `?hiddenMenu=1&tid=…`。**真机实测（真实浏览器 + 三个只有一行代码的变体扩展）却相反**：

| 规则 | 网址 | 结果 |
| --- | --- | --- |
| `*learn/*?tid=*` | `…/learn/X?tid=1` | 注入 |
| 同上 | `…/learn/X?a=2&tid=1` | **不注入** |
| `*learn/*?*` | `…/learn/X?a=2&tid=1` | 注入 |
| `*learn/*` | `…/learn/X?a=1&b=2&tid=3` | 注入 |

**结论**：`?tid=` 里的 `?` 是**查询串锚点**，规则要求它紧跟路径；**参数顺序一变就静默失效**。

**更值钱的推论**：那条规则里的 `?tid=` **对内容脚本毫无筛选价值**——脚本自己在运行时读 URL 参数，匹配规则写它只制造了一类"同域名同路径、只因参数顺序不同就不注入"的静默失败。**能用"更宽的匹配 + 脚本内部自查"解决的，别把判断塞进匹配规则。**

**方法论**：**文档说可以 ≠ 这个浏览器可以。** 匹配规则、事件时序、CSS 语义这类"宿主环境行为"，要么真机验证，要么用最小对照实验（只留一行代码的变体）验证，别靠推理。

## 四、【事实】改别人的状态语义 = 制造"按钮闪烁"

我把"准备页就绪"这个布尔量的判据从「准备页壳摘掉了隐藏类」改成「页面上有题目元素」，结果是：

```
题目渲染出来 → 该布尔量变 true → 作者显隐条件里的 !该布尔量 立刻变 false → 按钮被藏回去
```

表现就是用户说的"**闪一下就没了**"。而作业路径因为走的是 `|| 题型==='homework'`（不受这个布尔量影响），反而正常——**同一个 bug 在不同题型上表现不同，最容易把人带偏。**

**教训**：

1. 作者代码里但凡有个**布尔量同时被"状态判断"和"显隐判断"共用**，它就承载了两层语义。改它的定义前，先把它被引用的所有地方读完；
2. **引入新状态变量比改老变量语义安全**（我当时先走对了这一步，又因为"少改动"退回去，才反复）；
3. 症状若是"闪一下"，八成是**两个状态互相打架**，而不是某个状态错。

**同时**：我当时还犯了一个更基础的错——在脚本加载时**只检查一次**"页面是否就绪"。这类页面是**前端路由 + 客户端渲染**的：脚本在 `document_end` 跑的时候，题目往往还没渲染。**"就绪"必须轮询等待，不能在加载那一刻赌一次。**

## 五、【事实】旧类名在新前端会"无声失效"

原实现用 `f-dn` 隐藏按钮，旧前端有 `.f-dn{display:none}`；新前端是另一套原子化样式，**整批旧工具类都不存在**了。于是 `classList.add("f-dn")` 变成**空操作**，三个按钮全露出来——**元素在、逻辑也跑了，但样式语义丢了**。

这与"选择器找不到"是**两类不同的失效**，只测 `querySelector` 命中数会完全漏掉后者：

| 失效类型 | 表现 | 判据 |
| --- | --- | --- |
| 选择器不存在 | 元素找不到、功能不执行 | `querySelector` 命中 0 |
| **类名/样式不存在** | 元素在、逻辑跑完，但该藏的没藏 | 那个类名在页面 CSS 里搜不到 |
| 方法不存在 | 命中即抛错 | 该方法在这个环境里是不是原生方法 |

**顺带一条**：同一个方法名在两种环境下可能一个是原生、一个是库方法（例如 `prepend` 在原生 DOM 与 jQuery 上都有，语义还接近）。**"这个名字以前能用"不能证明"现在能用"，要看它是谁提供的。**

## 六、【事实】"看起来是整壳重写"，可能只是你抓错了页面

我拿到的新版页面 DOM 里，旧前端的十几个标记**全部为 0**，于是断定"整壳重写、选择器全废"，据此改了一大批东西。

**实际**：那份 DOM 是**新版课件页**抓的；而**答题页仍然是旧 DOM**——用户的测验/作业网址只是同一路径下多了个参数：

```
/learn/课程号?tid=…               ← 旧形态
/learn/课程号?hiddenMenu=1&tid=…  ← 新形态（只多了一个参数）
```

**教训**：平台改版常是"**部分页面迁移**"（栏目页换壳、答题页照旧）。判断"某类页面是否换壳"时，**必须抓那一类页面本身的 DOM**，不能用相邻页面（课件页 vs 答题页）替代。我为此白改了好几轮选择器与路由——**用户一句"旧路径依旧完美运行"才把我拉回来**。

**推论**：新前端同时存在**路径路由**（`/mooc/learn/{课程号}/content|assessments|exams`）与**hash 路由**（`#/learn/quiz?id=…` 这种答题页）两套导航。**不能按"整体换路由"一刀切**。

## 七、这份文档的"元教训"（最该记住的）

1. **先要"能判定"的证据，再动手。** 我早期几轮全是推理，每轮都"很有道理"，但判断不了"脚本到底进没进来"。后来改成让**程序自己报**——在每一层决策点打一行日志（注入了吗、容器是谁、状态翻没翻），一次就锁定了。
2. **不要用静默的写法。** `?.` 把 `null` 吞掉、`if (x) {…}` 没有 else、可选链后面的方法调用——这些都会把"失败"变成"什么都没发生"。**每个提前 return / 每个落空分支都要留痕**，否则下一次排障还要从头再来。
3. **改一层、验一次、只改一层。** 多因一果时，同时改三处会得到"还是不行"，而且分不清是哪处没生效。我一次改多处，结果用户看到的症状在"好了一点"和"更糟了"之间反复。
4. **用户的现象描述是最硬的证据。** "课程引导页上不该出现按钮"、"作业互评出现了、测验闪一下就没"、"旧路径依旧完美运行"——每一条都直接推翻了我一个错误假设。**先解释清楚用户看到的每个现象，再谈结论。**
5. **范围要收窄到"最小可验证"。** 用户明确说过"只修按钮不出现、别改逻辑实现"，我还是顺手改了一堆（候选选择器、React setter、额外状态、诊断日志）。**被要求最小改动时，"顺手"就是违规。**
6. **别人的项目，改动形态跟他的规范走**（日志留不留、README 写不写、注释风格），并且**擅自"顺手修 bug"要谨慎**——我"修"了一处空调用，虽然是对的，但它让 diff 变大、也让责任边界变模糊。
7. **上游可能已经修好了。** 我在中途看到服务器推的"新版本已发布，支持新 UI"提示，却继续埋头自己改。**动手前先确认上游版本与你手上这份的差距**——省下十几轮。
