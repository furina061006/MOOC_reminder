# 2026-10-19 v1.2.0 的 Release 晚了三天：裸 `git push` 不推 tag

用户报：「上次 tag 1.2.0 没有送到 release 里，只更新了仓库」。核查后确认：**远端根本没有
`v1.2.0` tag**，`release.yml` 的 `on: push: tags: v*` 从未被触发，Release 列表停在 v1.1.2。
代码和版本号都没问题，缺的只是一次 tag push。

## 1. 证据链

- **远端没有 tag**：`GET /repos/furina061006/MOOC_reminder/git/ref/tags/v1.2.0` → 404；
  `git ls-remote --tags origin` 只到 `v1.1.2`。这是唯一直接原因 —— 没有事件，workflow 不会跑。
- **本地时间线**（reflog，2026-10-16）：
  - `04:05:08` 合并 dsh → main（`86bec82`）；
  - `04:05:28` 创建 annotated tag `v1.2.0`（指向 `86bec82`）；
  - `04:06:59` `origin/main` 被 push 更新（reflog 记为 `update by push`）。

  tag 建在 push **之前**。如果那次 push 带了 tag，远端就会有——所以不是「tag 建晚了」，
  而是 push 时没带它。
- **git 配置**：`push.default` 未设置（默认 `simple`）、`push.followTags` 未设置、
  `remote.origin.push` 为空。结论：`git push` / `git push origin main` 只推当前分支。
- **旁证**：bash history 里 1.1.1 那次是显式推 tag 的（`git push origin main v1.1.1`）；
  1.2.0 没有对应的 tag push 命令。不过 history 只保留 2000 行且被其他项目挤占，
  这条只能当旁证，不能当铁证。

## 2. 排除项

- 仓库 **rulesets 为空**（没有 tag 保护规则会静默拒绝推 tag）；
- Actions 正常：v1.1.2 成功发布过，`release.yml` 也没改过；
- 版本一致：`manifest.json`、`package.json`、tag 都是 `1.2.0`，workflow 的版本校验会通过；
- 只可能是「tag 没到 GitHub」，不可能是「workflow 跑了但失败」——失败会在 run 列表留记录，
  而 v1.2.0 一条都没有。

## 3. 修复

```bash
git push https://github.com/furina061006/MOOC_reminder.git v1.2.0
```

本机 SSH 被 GitHub 拒绝（`Permission denied (publickey)`），实际走 HTTPS + git 凭据助手。
推上去 **33 秒后** Release 自动建好（`published_at` 2026-10-19T15:42:32Z），附件
`mooc-reminder-v1.2.0.zip`（629897 字节）。下载后与本地 `npm run package` 的产物解压
`diff -r` **逐文件一致**；两边 sha256 不同属正常——zip 头会写入每个文件的 mtime，
校验方式见 `operations.md`。

## 4. 两个容易误判的点

- **run 状态会骗人**：当天 GitHub Actions 处于 `degraded_performance`。发版 run
  （39279961077）在 API 里一直显示 `queued`、job 没有分配 runner，时间停在创建时刻；
  但 Release 与附件已经真实存在。说明 job 实际跑完了，只是状态上报坏了。**判断发版是否成功，
  只看 Release 与附件，不看 run 徽标。**
- **Release 的 `created_at` 是 tag 日期**：v1.2.0 显示 `2026-10-16`（tag 创建时间），
  真正发布时刻看 `published_at`（`2026-10-19`）。v1.1.2、v1.1.0 的 `created_at` 同样
  等于各自 tag 的时间，不是巧合。

## 5. 防再犯

- 发版时把分支和 tag 一起推：`git push origin main v1.2.0`（与 1.1.1 的实际做法一致）；
- 推完立刻自检：`git ls-remote --tags origin | grep v1.2.0`，空输出就是没推上去；
- `git push --follow-tags` 只推「推送时已存在、且从被推提交可达」的 annotated tag，
  tag 后补建的情况它同样不管——别把它当万能；
- 最终以「远端 tag + Release 附件」为准，而不是 push 的退出码或 Actions 的绿色徽标。
