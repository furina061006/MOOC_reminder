合并进 `main` → 在 `main` 上打 tag → 用户推送。

## 预检发现的四个事实（都不是猜的）

1. **没有任何测试守着 `manifest.json` 与 `package.json` 的版本同步**：`tests/unit/manifest.test.mjs`
   只断言 `manifest_version: 3`，release workflow 只比对 tag 与 `manifest.json`。所以漏改 `package.json`
   不会报错——只能靠人记得，已写进 `operations.md` 的发版流程。
2. **版本号在仓库里只出现在那两个文件里**。`grep -rn '1\.1\.0'` 的其它命中全是日志/文档叙述与测试夹具
   （还有 `package-lock.json` 里的 Node 版本要求），一律不该动。
3. **既有 tag 是 annotated**：`git cat-file -t v1.1.0` → `tag`（不是 `commit`）。所以 `v1.1.1` 也用
   `git tag -a`，保持同一种类型。
4. **本地打包与 CI 产物同源**：本地 `npm run package` 产出 `mooc-reminder-v1.1.1.zip` 为 **623398 字节**，
   用户推送后 GitHub Release 上的附件也是 **623398 字节**、40 个条目。打包配方单源（`tools/package-extension.mjs`）
   在这一点上得到了可验证的确认，写进了 `operations.md`。

发布前还本地模拟了一遍 workflow 的那道校验：`tag_version=1.1.1 == manifest_version=1.1.1` ✅，
并确认包内确实含这次的修复（`reconcileStatus` / `isNewerVersion(previous.latestVersion` /
「本次检查失败」三处都在 zip 里）。

## 事故：一个提交落到了 `main` 上（以及怎么捞回来的）

`fix(update)` 那个提交（本轮修复 1.1.1 内容的 `6e5445b`）最初是在 `main` 上创建的——**违反「开发只在
`dsh`」这条红线**。reflog 给出了原因：

```
6e5445b HEAD@{0}: commit: fix(update): ...
953d6b5 HEAD@{1}: checkout: moving from dsh to main   ← 不是我的命令
bc98c97 HEAD@{2}: checkout: moving from main to dsh   ← 我切回 dsh 之后
```

我切回 `dsh` 之后，**工作区的 HEAD 被另一个终端（用户为了推送而切分支）切到了 `main`**，我的提交就落在那里。
处理方式（关键是**先确认远端**再改写本地）：

1. 用 GitHub API 独立确认远端 `main` 仍是 `953d6b5`（我推不了、但有网）——脏提交没被推出去，
   所以本地改写不涉及「重写公开历史」；
2. `git checkout dsh && git cherry-pick 6e5445b` → `dsh` 得到 `fc82271`（内容相同、SHA 不同）；
3. `git branch -f main 953d6b5` 把 `main` 放回与 `origin/main` 一致的位置；
4. 校验 `git rev-parse main origin/main` 两者相同、`git diff --stat main dsh` 只剩该改的文件。

用户对此的态度是「这次就算了，下次注意」，并把「所有开发都要在 dsh 分支进行」又强调了一遍。
因此 `AGENTS.md` 的红线 1 补了一句：**提交前先 `git branch --show-current` 确认在 `dsh`**（工作区共享，
HEAD 可能被切走）。教训很直白：不要依赖「我上一次切到哪个分支」的印象。
