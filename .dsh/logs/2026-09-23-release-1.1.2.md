3. SW 的 `COURSE_LINKS`：锚点（非学习页）是**弱信号**，只能填空课程名，不能覆盖已有名字；

   「未知课程」——`main.js` 的注释此前声称 SW 不会这么做，实际会）；
   注册日志带上 `id="名字"(类型)` 与 `fromCoursePage:`，下次一眼能看出是谁登记的。

## 流程

1. `dsh` 上三个提交：`fix(courses): …` → `docs: …` → `release: 1.1.2`；
2. 合并 `dsh` → `main`（`--no-ff`，与历史一致）；
3. 在 `main` 上打 **annotated** tag `v1.1.2`；
4. **推送与 Release 由用户执行**：`git push origin main && git push origin v1.1.2`。
   推 tag 会触发 `.github/workflows/release.yml`：校验 tag 与 manifest 版本一致 → `npm run validate`
   → 打包 → `gh release create --generate-notes`。

## 关于 Release 说明（用户问）

workflow 用的是 `gh release create --generate-notes`，所以**默认正文是 GitHub 按
`compare/v1.1.1...v1.1.2` 自动生成的提交列表**（不是 changelog 的内容）。想写「修复了什么」有两条路：

- **发布后直接在 Release 页面编辑正文**（成本最低；自动生成的内容已经按提交列好了，改成人话即可）；
- 想固定成策展文案：把 workflow 的 `--generate-notes` 换成 `--notes-file <文件>`，文件内容取自
  `changelog.md` 的对应小节（需要一次额外的 workflow 改动与「从 changelog 提取小节」的脚本）。

本次采用第一条：发布后把 `changelog.md` 的 1.1.2 小节贴进 Release 正文即可。
